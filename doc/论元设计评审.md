# 论元（槽位）设计评审

数据基础：200 篇 / 719 事件 / 1726 论元（`data/dataset/ee_{train,dev,test}.jsonl`）。
代码基础：`extract/kg_extract.py` 的 `RELATIONS`、`DOMAIN`、`TYPE_SLOTS`、`SLOT_DOMAIN_OVERRIDE`。

---

## 一、总体判断

**骨架是对的，但「通用角色」这一层设计没做完，导致语义重叠和约束失效。**

三个明显的进步值得保留：

1. 把「使用」拆成发射平台/发射物，这个改对了。实测 312 个对抗事件里发射物用了 61 次、发射平台 22 次，能回答「用什么打的」和「打出去的是什么」两个不同问题。
2. 受事/打击对象分开，方向正确。93 次并存中只有 4 次同值重复，说明模型多数时候能区分「谁被打了」和「打了什么」。
3. 表态内容补上后，声明类从「只剩一个谁说的」变成 69/111 有内容。

但有四类问题需要处理，其中两个是结构性的。

---

## 二、结构性问题

### 问题 1：通用角色没有统一定义，靠注释约定

`RELATIONS` 里注释写「通用角色，所有事件类型都可有」，列了四个：

```106:106:extract/kg_extract.py
    # 通用角色，所有事件类型都可有
    "施事", "受事", "涉及", "包含",
```

但代码里没有 `COMMON_ROLES` 常量。第 1658 行的校验写的是硬编码元组：

```1657:1658:extract/kg_extract.py
                if name in ("施事", "涉及", "包含", "到场"):
                    pass  # 通用角色对所有类型开放
```

注意这里比注释少了「受事」。也就是说注释说受事是通用的，代码却没把它当通用处理——受事只能靠 `TYPE_SLOTS` 里逐条列出来才合法。

**后果**：这个不一致直接导致了你上一轮看到的「施事全变成受事」——我按 `TYPE_SLOTS` 建下拉框，漏了不在表里的通用角色。同一个根因，在抽取侧表现为约束口径不一致，在前端表现为显示错误。

**建议**：定义单一常量，三处共用。

```python
COMMON_ROLES = ("施事", "受事", "涉及")   # 包含 是事件层级，单独处理
```
`TYPE_SLOTS` 只写专属槽位，`DOMAIN` 校验和 `annotate/tasks.py` 都从这里取。

### 问题 2：「施事」与专属角色大面积语义重复

实测同一事件里施事与专属角色并存 25 次，其中 **15 次值完全相同**：

| 类型 | 并存组合 | 值相同 |
| --- | --- | --- |
| 合作 | 施事 + 甲方 | 4/12 |
| 部署 | 施事 + 兵力 | 0/22 |
| 表态 | 施事 + 表态方 | 1/6 |
| 治理 | 施事 + 主体 | 1/2 |

实例：

```
合作·签署   施事=泰国第一军区   甲方=泰国第一军区
表态·声明   施事=伊朗武装部队哈塔姆安比亚中央总部   表态方=伊朗武装部队哈塔姆安比亚中央总部
治理·行政   施事=内务部         主体=内务部
```

**这是设计层面的问题，不是模型抽错**：既然表态类有「表态方」、合作类有「甲方」、治理类有「主体」，这些角色本身就承担了「谁做的」，再叠加一个通用「施事」必然重复。

下游代价很实在：查「某事件谁发起的」得同时查施事、表态方、甲方、主体四个槽位，还得去重；做 Arg-F1 时同一实体被算两次。

**建议**（三选一，推荐 A）：

- **A. 收窄施事适用范围**：施事只在没有专属施动角色的类型上开放（对抗、灾伤、其他、部署）。合作/表态/治理只用自己的专属角色，`SLOT_DOMAIN_OVERRIDE` 里禁掉这三个类型的施事。
- **B. 反向归一**：删掉表态方/甲方/主体，统一用施事 + 另一个槽位区分方向。改动大，且「甲方/乙方」的双边语义会丢，不推荐。
- **C. 保留现状**，在规范里明说「专属角色优先，施事仅在专属角色缺失时填」。最省事，但需要校验阶段做互斥检查，否则模型仍会双填。

部署类的 22 次并存值都不同（施事是国家/机构，兵力是装备/部队），这是合理的，不受影响。

## 三、约束失效问题

### 问题 3：「打击对象」收国家，与「受事」的边界被自己破坏

文档写得很清楚：

```202:211:doc/本体与关系设计方案.md
**受事、打击对象、拦截对象的分工**是这一层最容易混的地方：
  受事 → 哈马斯              （被打的组织）
  打击对象 → 指挥所          （被打的具体设施）
早期三者在同一槽位里混用…现在受事只收国家/机构/人物/装备，地点一律走打击对象。
```

但 `DOMAIN` 给打击对象也开了国家：

```133:133:extract/kg_extract.py
    "打击对象": ({"事件"}, {"地点", "机构", "装备", "国家"}),
```

实测 304 条打击对象里，**17 条（5.6%）值是纯国家名**（科威特 3、伊拉克 3、黎巴嫩 3…）。这些本该进受事。

「国家」这一项的加入可能源自早期「国家名不再兼作地点」的补偿（文档第 43 行提到过阿联酋终点被丢的教训），但用在打击对象上是过度补偿——它把刚分开的两个槽位又粘回去了。

**建议**：打击对象去掉「国家」，只留 `{地点, 机构, 装备}`。若担心国家名当目标（如「打击伊朗」），那属于受事，不是打击对象。

### 问题 4：零论元与关键槽位漏填

66 个事件（9.2%）完全没有论元，其中不少是明显可填的：

```
对抗·打击  以军当天袭击了位于伊朗南部布什尔市的伊朗"主要天然气设施"
           → 施事=以军，受事=伊朗，打击对象=天然气设施，一个都没抽到
表态·声明  美国总统特朗普9日在社交媒体发文说，美军一架"阿帕奇"武装直升机…被伊朗…
           → 表态方=特朗普，对象=伊朗，内容齐全，全空了
```

部署类有 30 个事件文本里提到了地点，却没有起终点。其中「战备」占了一半以上：

```
部署·战备  日本多地加强军事部署
部署·战备  以色列国防部长卡茨28日指示以军扩大在约旦河西岸的军事行动
部署·演习  海上演习将于16日至17日在日本海举行
```

根因是 `TYPE_SLOTS` 给「战备」只留了 `{兵力}`：

```187:187:extract/kg_extract.py
    ("部署", "战备"): {"兵力"},
```

但「战备」在真实语料里几乎总要交代「在哪备战」。这是一个槽位设计与语料不匹配的例子。

**建议**：
- 「战备」补 `{终点}`（备战区域）。
- 「演习」已有起终点，但 13 个事件里只有 5 个填了终点，需要在提示词里加重。

## 四、次要问题

### 问题 5：字面值槽位实为 span，却按自由文本处理

`战果`/`伤亡数字`/`表态内容`/`议题`/`结果`/`目的`/`处置结果`/`原因` 共 197 条（11.4%），其中 **196 条能在原文精确匹配到**。也就是说它们实际上是文本片段，不是自由填写的值。

但当前设计把它们当「字面值」自由生成，代价是：
- 无法做 offset 对齐，标注端不能框选校正
- 模型改写一字就破坏可追溯性（唯一那条不在原文的 `原因=伊朗导弹袭击以色列致2人死亡` 就是改写产物）

**建议**：字面值槽位改为「从原文摘录连续片段」，并在抽取结果里带 `start/end`。这样前端可以像实体一样框选，校对效率会明显提升。

### 问题 6：`原因` 的边界没定住

实测 7 条「原因」，值长这样：

```
伊朗伊斯兰革命卫队导弹部队向这些武装…
当地时间6月14日，乌克兰国家安全局…
一艘由土耳其所有、悬挂巴拿马国旗的货…
```

把整句话当原因填进去了。而 `DOMAIN` 允许 `{事件, 字面值}` 两种，模型倾向于走字面值这条宽松路径。

**建议**：优先连事件（`原因 → 事件`），只有无法成事件时才用短语，且限制长度。

### 问题 7：`包含` 边为 0

复合事件设计在文档里占了一节，`PLANNED_FORBIDDEN` 都专门提到了 `包含`，但实测 **0 条**。`extract/composite.py` 的 `compose_events()` 没接进 `kg_batch.py` 主流程。

这不算设计错误，是未实现。但设计文档里把它当既有能力写，会误导后续。

### 问题 8：`其他` 类没有槽位定义

29 个「其他」事件产出了打击对象、战果、终点、起点、兵力（共 6 条越界）。因为 `TYPE_SLOTS` 里没有 `("其他", "")` 这一项，校验时走的是「未列出 = 全部禁止」还是「未列出 = 不限制」，口径不明。

上一轮我在前端做了全量开放兜底，但抽取侧应该明确：要么给「其他」定一组通用槽位，要么明说该类不做槽位约束。

## 五、优先级建议

| 优先级 | 问题 | 动作 | 预期收益 |
| --- | --- | --- | --- |
| P0 | 问题 1 通用角色无单一常量 | 抽 `COMMON_ROLES`，三处共用 | 消除约束口径不一致，防止同类 bug |
| P0 | 问题 3 打击对象收国家 | 去掉「国家」 | 5.6% 打击对象回归受事，边界清晰 |
| P1 | 问题 2 施事与专属角色重叠 | 施事限定在对抗日照/灾伤/其他/部署 | 15 次重复消失，Arg-F1 不再重复计分 |

## 六、一个可以直接复用的判断标准

评审槽位设计是否合理，我建议用这三条卡：

1. **互斥性**：同一事件里，两个槽位会不会装同一个值？若会，说明职责没分清（问题 2、3）。
2. **可判定性**：给定一个句子，标注员能否不查文档就判断该填哪个槽？靠 5 条正例 3 条反例才分得清的，通常该合并或改定义（受事/打击对象接近这个边界）。
3. **必有性**：这个槽位在真实语料里出现频率多高？若某类型 90% 的事件都缺某槽位，要么槽位定义不匹配语料，要么该类型划分有问题（战备缺终点、表态缺内容都踩过）。

按这三条，当前 28 个槽位里，`施事`、`打击对象`、`原因`、`战果` 四个需要动，其余可用。
