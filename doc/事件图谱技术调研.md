## 二、核心概念

### 2.1 事件是什么

> 事件是指在特定时间、空间下，由一个或多个角色（事件主体）参与，围绕某个主题开展的一系列活动。

> 事件知识的复杂性在于事件并不会对应到现实世界中的某一个具体的实体，它是一系列实体，以不同的角色在一段时间内参与活动的一个抽象。

### 2.2 事件图谱与实体图谱的关系

这是两篇里最精炼的表述，解释了为什么事件必须是独立节点：

> 实体图谱描述实体属性和实体之间的关系，它基本上是静态的，而事件图谱则描述客观世界的动态变化，并且侧重多个实体之间的动作。**如果实体的属性或者关系发生了变化，那么就是一个事件发生了。**

> 在任意时刻，**一个事件可以映射到实体图谱上的一个子图**，因为事件有参与的角色，而事件主体可以映射到实体图谱上的实体，这样就建立了事件图谱和实体图谱之间的关联，两者之间可以进行相互推断。

推论：事件是实体子图的时间快照。把事件当作实体的一种，会混淆「静态结构」与「动态变化」两层语义。

### 2.3 为什么要做事件图谱

两条理由：

**一、事件更符合人对世界的理解层次。** 以「桃园三结义」图为例：无知识时只知道有三个人和树；有实体知识时知道是刘备、关羽、张飞和桃树；有事件知识时才知道「东汉末年三人在桃园结义」。只有到事件层次，理解才完整。

**二、事件图谱能对动态世界建模。** 实体图谱只保留最新状态，事件图谱能把属性与关系的变化过程建模，并与触发变化的事件一一对应。

### 2.4 事件图谱的三层结构

| 层 | 作用 | 与实体图谱的关系 |
| --- | --- | --- |
| 本体层 | 事件类型与角色定义，类比实体图谱的 schema | 独立 |
| 事件层 | 事件与事件之间的关系 | 独立 |
| 论元层 | 事件参与角色 | 论元可映射到实体，与实体图谱关联 |

## 三、构建流程

### 3.1 顺序与实体图谱相反

> 传统知识图谱会先定义 schema，然后进行抽取与归一，最后入库。而事件图谱由于缺少可参考的结构化来源，需要先进行事件检测，在检测出大量事件的基础上，才能进行后续操作（构建表示体系、抽取等）。

顺序是：**事件检测 → 事件表示（类型体系）→ 事件抽取 → 关系挖掘**。

传统图谱有垂类站点、百科等结构化来源，可先定 schema；事件没有这类来源，schema 只能从数据中归纳。

### 3.2 事件检测

目标：快、准、全地收录客观事件。三个挑战：

1. 网页资讯存在大量非事件内容
2. 事件粒度复杂，父事件与子事件常同篇出现，聚类易形成大簇而漏掉小事件
3. 时效要求高，多数场景需分钟级延迟

方案：基于多任务学习的三段流程——识别非事件内容、抽取事件名片段、事件归一。多个策略模型经多任务学习后相互增强，资源消耗降低而各自效果提升。

效果：分钟级收录，准确率与覆盖率均达 90% 以上。

### 3.3 事件表示（类型体系）

与实体 schema 挖掘的关键差异：实体有垂类站点可参考（如电影查豆瓣即知导演、编剧、主演字段），事件没有。

> 「破产」这个事件类型，从类型名可以知道该事件可能会有一个「破产人」属性，但「债权人」这个属性就必须从该类型相关的正文中才能找到。

方案：开放类型挖掘 + 人工校验。先从事件库挖掘类型并构建层次，再针对每个类型召回相关资讯做角色挖掘，最后人工校验。

规模：几十个领域，几千个事件类型，一万多个事件角色。

### 3.4 事件抽取

三种方案，各有取舍：

| 方案 | 做法 | 优势 | 局限 |
| --- | --- | --- | --- |
| 通用属性抽取 | ERNIE + Bi-LSTM + CRF 多属性联合抽取，抽取后归一（地点归一、时间规范化、参与者实体化） | 一次抽取多个属性，效率高 | 无法灵活泛化到新类型 |
| 自定义论元抽取 | 基于阅读理解问答，三轮提问：触发词 → 事件类型 → 各角色 | 类型与角色解耦，少样本甚至零样本 | 效率低，每个角色需单独提问 |
| 语义角色抽取 | 把类型耦合角色解耦为通用语义角色，多层指针网络一次抽取 | 兼顾灵活性与效率 | 需预先定义语义角色体系 |

**语义角色解耦是其中最值得借鉴的思路。** 原话：

> 「收购」类型和角色「收购价格」「被收购方」「收购方」是耦合的。如果把所有这样的类型角色转化为如「数值」「受事主体」「实施主体」这样的与类型解耦的语义角色，我们整体的角色数量就可以从 n×类型数 这一数量级，降低到只有十几个语义角色的量级。

参照：公开数据集 ACE2005 上论元分类任务 F1 约 60%，学术效果尚未达到直接可用。

### 3.5 事件关系挖掘

定义了四种事件间关系：

| 关系 | 说明 |
| --- | --- |
| 从属 | 父事件与子事件的层级 |
| 共指 | 不同表述指向同一事件 |
| 时序 | 事件的先后顺序 |
| 因果 | 事件间的因果链 |

**因果关系的处理思路值得注意**——不追求判定正确性，而是当作观点：

> 因果关系不是绝对的、客观的，它只是人类对我们过去经验的一种主观总结。（引休谟「明天的太阳未必会升起」）

> 我们把因果关系当作观点来看待，直接绕过这个正确性的问题。通过因果的出现次数、来源的权威性等方面来评价抽取出的因果的质量。

技术上按序列标注处理，同时标注多因多果；通过事件归一，把分散在不同篇章的同一因果表达聚合到同一图谱，缓解因果稀疏。

成果：因果图谱节点正确率 90% 以上，规模达百万量级。

### 3.6 推理的三个层次

| 层次 | 做法 | 适用 |
| --- | --- | --- |
| 事理图谱 | 抽象事件的因果规律。「某天美国加息」是具体事件，「美国加息」是抽象事件；后者常导致「美元汇率上升」，故新一次加息也可推断汇率上升 | 泛化推理 |
| 规则推理 | 从一系列因果中挖掘规则。如「上游库存不足 → 下游价格上涨」，可迁移到钢铁等行业 | 单步、有领域规律 |
| 图神经网络 | 把事件节点放入全图做边预测，支持多步推理。如「黄光裕出狱 → 他是国美高管 → 国美股票大涨」 | 多步、复杂链路 |

## 五、行业图谱与通用图谱的差异

这条对本项目直接适用——军事态势分析属于典型的「行业」需求：

| 维度 | 通用知识图谱 | 行业知识图谱 |
| --- | --- | --- |
| 表示 | SPO 三元组足够 | 需表示时序、事件、流程等复杂知识 |
| 数据 | 互联网开放域 | 知识空间封闭，缺标注数据，专家标注成本高 |
| 服务 | 离线、平台化、在线 | 私有化、组件化 |
| 应用 | 理解为主（问答、推荐） | 需推理计算乃至决策 |

## 六、对本项目的启示

### 6.1 与本项目对照

| 维度 | 百度 | 本项目 | 差异性质 |
| --- | --- | --- | --- |
| 实体规模 | 50 亿 | 22,809 | 目标不同，不需对齐 |
| 事件规模 | 千万级 | 11,385 | 同上 |
| 事件类型 | 4300 余种 | 5 类性质 × 19 类动作 | 粒度取向不同 |
| 论元角色 | 一万多个（类型耦合） | 6 种（已解耦） | 本项目已采用解耦思路 |
| 事件间关系 | 4 种（从属、共指、时序、因果） | 1 种（包含） | **明显缺失** |
| 更新方式 | 分钟级实时 | 离线批处理 | 场景不同 |

### 6.2 已做对的三点

**事件作为独立节点。** 「事件映射到实体子图」的定位与我们的设计一致：事件不算实体，通过角色关系连接实体。

**论元角色解耦。** 我们用的是施事、受事、到场、使用、涉及、表态六种通用角色，而不是为每个事件类型定义专属角色。这正是百度「语义角色抽取」的做法。

**关系名只表语义角色。** 动作类型放在事件的 `event_type` 上，不混进关系名。这与「实施」这类万能桶的拆分方向一致。

### 6.3 明显缺失：事件间关系

四种关系里我们只有一种：

| 关系 | 状态 | 影响 |
| --- | --- | --- |
| 从属 | 有（`包含`），但实测仅 3 条 | 复合事件未生成，等于没有 |
| 时序 | 无 | 无法表达事件的先后，态势演化的基础缺失 |
| 因果 | 无 | 无法表达归因与后果 |
| 共指 | 无 | 同一事件的多篇报道无法聚合 |

**时序与因果是态势分析的核心。** 现在图上是事件星形结构，事件之间没有边，无法回答「先发生了什么、由此导致什么」。

### 6.4 可借鉴的两条思路

**因果关系当观点处理。** 军事新闻里的归因大量是单方宣称（「此次袭击是对 X 的报复」），直接判对错不可行。可按百度的做法：存为带来源的因果陈述，用来源权威性与提及次数加权，标注时只判「原文是否表达了因果」，不判「因果是否成立」。

**先检测后归纳的构建顺序。** 我们目前是先定本体再抽取。若将来扩到万篇以上或换领域，可考虑反向流程：先跑开放抽取，从结果里归纳类型体系，再回头规范。

## 七、待评估的改进项

按优先级排列，均未实施：

1. **补时序关系。** 同一篇或同一事件簇内，事件按时间排序连边。数据上只需事件的 `publish_time` 与原文时间短语，成本低。
2. **修复合事件生成。** 当前 `composites` 全部为空，`包含` 边仅 3 条，与设计不符，需排查 `extract/composite.py` 未生效的原因。
3. **评估因果关系的可行性。** 参照「当作观点」的思路，先小样本试标，看标注一致性。
4. **考虑共指聚合。** 跨篇的同一事件归一，与现有的 `align.disamb` 事件融合有重叠，可复用。
