# 实体体系评审

数据基础：`data/extract/kgv9_huanqiu_mil_2026-01.jsonl`（200 篇 / 1145 条实体 / 653 个去重实体）。

---

## 一、结论

**六类划分本身没问题，执行质量也高**——1145 条实体里只有 1 个类型冲突（「弹药库」被同时标成地点和装备），国家名零误标。

**但有三类问题会直接破坏图谱的可视化**，其中第一个最严重：

| 问题 | 规模 | 对可视化的影响 |
| --- | --- | --- |
| 简称与全称并存 | 4 组高频机构 | 同一支部队显示成两个节点 |
| 泛称设施被当实体 | 10 个，246 个地点里混入 | 无法定位到国家，成为孤立节点 |
| 装备只用通名 | 32 篇用「无人机」 | 图谱里 32 条边指向同一个「无人机」节点 |

## 三、最严重的问题：简称与全称没归一

同一支部队被拆成两个节点：

| 简称 | 篇数 | 全称 | 篇数 |
| --- | --- | --- | --- |
| 以军 | 4 | 以色列国防军 | 28 |
| 乌军 | 5 | 乌克兰武装部队 | 1 |
| 黎真主党 | 3 | 黎巴嫩真主党 | 10 |
| 哈马斯 | 3 | 巴勒斯坦伊斯兰抵抗运动（哈马斯） | 2 |
| 胡塞武装 | 6 | 也门胡塞武装 | 2 |

**这不是抽取错误，是缺一层实体对齐。**当前 `entities` 里每条都是原文片段，抽取时不做跨篇归并。图谱可视化时，「以军」和「以色列国防军」会是两个独立节点，各连一半的边，看不出这是一支部队。

军事领域这个问题尤其严重，因为简称极其常用：以军、俄军、乌军、美军、叙军、黎真主党、胡塞。

**建议**：加一层实体别名对齐（entity linking），维护一份别名表：

```python
ALIAS = {
    "以军": "以色列国防军",
    "俄军": "俄罗斯武装力量",
    "乌军": "乌克兰武装部队",
    "美军": "美国武装力量",
    "黎真主党": "黎巴嫩真主党",
    "胡塞武装": "也门胡塞武装",
    "杰哈德": "巴勒斯坦伊斯兰圣战组织",
}
```

但要注意：归一之后节点名该用全称还是原文？我建议**节点名用规范全称，另存 `aliases` 列表记录原文出现形式**，这样既统一又能追溯。

## 四、第二严重：泛称设施被当实体

10 个泛称被标成地点：

```
港口 3篇、美军基地 2篇、石油化工设施 2篇、石油设施 2篇、物流中心 2篇、
弹药库 2篇、总部 1篇、军事基地 1篇、武器库 1篇、炼油厂 1篇
```

还有一批带修饰的复合形式：

```
伊朗港口、美军位于科威特一基地、以色列境内的空军基地、
俄罗斯境内同类基础设施、能源基础设施、交通基础设施、民用设施、设施
```

**问题在于这些概念无法参与国别归属。**「港口」属于哪个国家？「弹药库」在哪？它们在图谱里只能成为孤立节点或错误的归属边。

对比之下，真正的专名设施是好实体：

```
那霸基地、百里空军基地、阿里·萨利姆空军基地、温赖特基地、
扎波罗热核电站、布什尔核电站、纳坦兹核设施、斯普利特港口
```

**建议**：区分「专名设施」与「泛称设施」。

- 专名设施（含具体基地名、核电站名）→ 保留为「地点」
- 泛称设施（港口、弹药库、军事基地、能源基础设施）→ **不作为实体**，只作为论元里的 `字面值`（打击对象的值可以是「弹药库」，但不建节点）

这与现有设计里「战果」「表态内容」走字面值的处理一致——不是所有信息都需要成为图节点。

## 五、第三：装备只有通名，没有型号

出现次数最多的装备实体：

```
无人机 32篇、导弹 15篇、防空系统 5篇、坦克 2篇、军舰 2篇、
火箭弹 2篇、战斗机 2篇、战机 1篇、炮弹 1篇、火炮 1篇、舰艇 1篇
```

106 个装备实体里，泛称占了主流。而提示词其实写了「原文有型号就抽型号，没有才抽通名」——说明大部分原文确实只写了「无人机」。

**问题**：「无人机」这个节点会聚集 32 篇的边，但它没有型号、没有归属、没有性能，在图谱里几乎没有信息量。而真正的型号节点（F-35、MQ-9、苏-27）反而很少。

**建议**两个选项：

- **A（推荐）**：装备泛称不进图，作为论元的字面值处理。只有带型号或专名（F-35、林肯号、爱国者系统）才建装备节点。这样装备节点从 106 个降到约 40 个，但每个都有实际信息。
- **B**：保留泛称节点，但给它加一个 `generic: true` 标记，可视化时可选隐藏。

我倾向 A，因为泛称装备无法回答「用什么打的」这个本体设计时的核心问题——而这正是当初把「使用」拆成「发射平台/发射物」的初衷。

## 六、其他小问题

### 6.1 「弹药库」类型冲突

唯一的多类型冲突：

```
弹药库  {'地点': 1, '装备': 1}
```

它是设施（地点），不是装备。按第四节的建议，它应该直接不进图。

### 6.2 机构名自解释，重复编码信息

```
中国驻符拉迪沃斯托克总领事馆    （名称含国家+地点）
驻日美军基地                    （名称含国家+地点）
伊朗军事指挥中心                 （名称含国家）
```

这类名称已经自带国别和地点信息，但仍需单独建辖属/驻地边。规则上没问题（节点名与边不冲突），但要注意**泛称化的「驻日美军基地」应该按第四节处理，不进图**。

### 6.3 国家类型零误标，兜底有效

`is_country()` 的强制归类型起了作用：33 个国家实体，0 个被标成机构或地点。这条逻辑应该保留。

### 6.4 人物、作品类型干净

人物 67 个，无职务串混入；作品仅 6 个（联合声明、安保三文件、南海行为准则、国防预算案等），都是合理实体。

## 八、实施结果

新增 `extract/entity_norm.py` 作为抽取后的归一与降级层，接在 `dataset.build` 之前。

| 指标 | 归一前 | 归一后 |
| --- | --- | --- |
| 实体去重 | 654 | **581** |
| 装备实体 | 171 | **63** |
| 地点实体 | 296 | **269** |
| 关系总数 | 1926 | **1926**（全部保留） |
| 论元总数 | 1851 | **1851**（其中 161 条标记 literal） |

关键设计取舍：**泛称端点不丢弃关系，而是打 `literal` 标记**。原方案直接丢弃会导致 162 条关系消失，其中包括 18 条「发射物=无人机」这类关键信息——用户需要知道「用无人机打的」，只是不需要建一个「无人机」节点。现在信息保留在论元里，节点不再生成。

别名记录的形态：

```json
{"text": "以色列国防军", "type": "机构", "aliases": ["以军"]}
```

校对脚本相应调整：论元值是规范名时，只要其别名出现在正文中，不再判为「值不在正文」（排除 61 条误报）。

---

## 八、一句话总结

**六类类型不用改，但「什么算实体」这条线要往里收一收。**

现在的问题不是类型分错，而是**把不该建节点的东西建成了节点**（泛称设施、通名装备），同时**把该合并的节点拆开了**（简称与全称）。

前者让图谱多出大量孤立节点，后者让同一实体分成两半。这两个问题都只在可视化时才暴露出来，在 F1 指标上反而可能看不出来——因为评测是按原文片段匹配的。
